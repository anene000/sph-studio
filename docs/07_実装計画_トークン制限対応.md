## 1. リマップの狙い

AI エージェント（Claude Code）による実装は 1 セッションのトークン量に上限がある。
そこで作業を **「1ユニット = 1セッションで完了できる」粒度**に分割し、各ユニットに
**目的・触るファイル・完了条件（DoD）・検証コマンド**を明示する。
ユニットは前から順に独立して着手でき、途中再開しても文脈が最小で済むようにする。

**設計原則:**
1. 1ユニットの変更ファイルは概ね 3〜6 個、追加行は数百行以内。
2. 各ユニットは「そのユニット単体で `lint`/`build`/`test` が通る」状態で終える。
3. UI と API は **共通スキーマ（`packages` の型 or 生成物）** を先に固定し、以後参照するだけにする。
4. 大きな一枚岩の画面は「レイアウト → 個別パネル → 連携」に分割する。

## 2. 開発モードの段階

| Phase | 実行形態 | 内容 |
|-------|----------|------|
| **A（先行）** | Python 別プロセス起動 | `backend`(uvicorn) と `apps/web`(next dev) を別々に起動。`solver` はサブプロセス。まず機能を作り切る |
| **B（同梱）** | Tauri + PyInstaller | `backend` を PyInstaller でバイナリ化し Tauri sidecar 化。1アプリとして配布 |

Phase A で①〜⑦を満たしてから Phase B に移る。Phase A の API 契約は Phase B でも不変。

## 4. ユニット・テンプレート（各セッションの進め方）

各ユニット着手時に、以下だけを文脈として与えれば再開できる。

```
- 対象ユニット: U?
- 参照: docs/03(仕様) の該当節, docs/07(本書) の DoD, lib/schema or models
- 触るファイル: （表の「主な対象」）
- 完了条件: DoD を満たし lint/build/test green、コミット
- 検証: 表の検証コマンド
```

## 5. ユニット別 検証コマンド（例）

| U | 検証 |
|---|------|
| U0 | `pnpm i` / `python -m venv` 手順が通る |
| U1 | `pnpm --filter web test` / `pytest backend -k schema` |
| U2 | `python solver/run_headless.py --scene_file data/scenes/sample.json --output_dir /tmp/out`（CSV/JSONL 生成） |
| U3–U6 | `pytest backend`、`uvicorn` 起動スモーク、`curl` で各 API |
| U7–U15 | `pnpm --filter web dev` で画面表示、`pnpm --filter web build` |
| U16 | e2e（新規計算フロー） |
| U18–U20 | `tauri build`（OS matrix） |
